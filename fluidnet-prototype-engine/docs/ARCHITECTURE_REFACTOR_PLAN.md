# 架构整理执行计划

制定日期：2026-11-03。代码基线：`7424576`；配套说明为本地已更新的 [当前架构图](ARCHITECTURE_AND_SEQUENCE.md)。状态：**AR-0～AR-6 已验证，AR-7 以本地记录与 PR #8 完整门禁共同验收**。

目标是降低新增设备、控制和建模功能时的连锁改动：保留现有单服务架构、物理求解器、Worker 接受事务和持久化机制，集中项目状态的写入入口，并消除热／制冷会话对流体会话的继承依赖。

本计划可以按编号顺序直接实施。每包完成代码、相关测试和证据登记后再推进下一包；执行期间常规实现选择由执行者处理，不要求逐包确认。本文的模块与接口现已实现；分包记录见下表，完整门禁见 [PR #8 检查](https://github.com/kongbaifan/fluidnet/pull/8/checks)。

## 2. 目标边界

### 2.1 前端

| 模块 | 本轮职责 | 状态与副作用约束 |
| --- | --- | --- |
| `project-model.js`（新增） | 参数默认值、显示／规范单位转换、模块快照到界面对象、规范项目导入及单项目文档组装 | 纯转换；不调用 HTTP、DOM 或 localStorage。已有内置参数映射与 Python manifest 规则必须显式保留 |
| `project-state.js`（新增） | 项目替换、参数草稿／应用、拓扑编辑及撤销／重做的统一操作入口 | 按项目 ID 定位；统一登记修改与结果过期；失败操作不留下部分更新 |
| `project-run-state.js`（新增） | 运行回包归属、帧合并、运行状态与历史查看 | 区分当前运行与历史档案；迟到响应不能覆盖当前编辑状态或另一个运行 |
| `project-links.js`（已有） | 端口占用、跨页连接、设备移页与关联清理 | 保留算法，由项目操作入口调用，结果仍使用当前五项 edge 格式 |
| `project-services.js` / `engine-client.js` | HTTP、保存队列、修订回执、运行请求与轮询 | 使用公共转换和状态操作，保留请求幂等、修订冲突与持久确认行为 |
| `studio.js` / 功能页面脚本 | DOM、交互与展示，调用上述模块 | 四类目标写入全部迁移；不以文件行数作为完成标准，不将其他编辑器功能顺带重写 |

运行时仍可使用当前项目对象结构，序列化后的文件格式保持一致。`draft` 是待应用输入，`params` 是已应用输入，运行请求是固定快照，历史结果只按其对应快照解释。localStorage 作为备份／缓存，服务端保存回执决定“已保存”状态。

计算合同继续由 Python `bridge.normalize_prototype_export` 和 Pydantic 校验；前端转换模块负责显示、文档组装及导入适配，不再造一个前端物理编译器。

### 2.2 后端

目标继承关系：

```text
SessionBase（新增：公共控制、参数命令、修订与资源生命周期）
├─ SimulationSession（流体、湿空气、风水联算）
└─ ThermalSession（热系统及现有热步进基础）
   ├─ ColdStoreSession（冷库 A）
   └─ StationSession（集总制冷站）
      └─ CoupledStationSession（制冷站与液体热耦合）
```

本轮解除 `ThermalSession → SimulationSession` 的依赖；保留已具备实际复用关系的热／制冷继承，不强行统一所有物理推进流程。

`SessionBase` 负责公共参数路由与所有权检查、PID／脚本调度、公共控制检查点、参数修订和资源清理。物理实现通过明确的内部钩子负责：整批参数的物理合法性检查、参数生效、参数附带状态的捕获／恢复、变量快照与域内资源释放。

钩子目标为 `validate_parameter_batch`、`apply_parameter_changes`、`capture_parameter_effects`、`restore_parameter_effects` 和 `close_domain_resources`。名称可随现有命名习惯调整，职责必须可单独核对。困液、支路开闭、水箱热量和湿空气校验留在流体域；制冷质量／能量、日程、缓存、适应步长及模块接受段留在各自域。

公共层不能依赖 `solver`、`trapped`、`air_*` 或具体制冷会话，也不能通过要求所有网络补齐空流体字段来工作。`ModuleStepTransaction` 的 prepare／validate／promote／synchronize 顺序保持原样；公共层不接管物理接受点。

### AR-1～AR-3：前端切换细节

- 先提取现有行为，再切换调用点，最后移除重复实现。转换函数不得顺带规范化或改写历史模块源码、哈希和单位定义。
- 内置参数别名、manifest 参数、绝对温度与温差、开度百分比、工况稀疏覆盖、布尔／文本／曲线参数均在转换清单内。
- 项目修改必须按稳定 ID 定位；异步回调不能仅凭当时的“活动项目”写入。保存回执到达前发生的新编辑继续保持 dirty；旧结果仍可作为历史查看，但不能标记成当前配置的新结果。
- 更新正在通过正则截取 `studio.js` 函数的单元测试，使其调用新模块入口。保留原有行为断言，避免把函数位置、文件长度或函数名字作为功能验收。
- 依赖注入沿用当前窗口工厂模式，新增文件加入 `index.html` 和 `npm run check`；新增测试加入 `test:ui`。

### AR-4～AR-6：会话切换细节

- 参数操作保持“整批候选校验 → 域内应用 → 一次修订”的顺序。组合公开参数的多目标写入全部遍历，不允许提前退出而漏掉目标。
- 控制检查点同时覆盖公共参数／修订／PID／脚本提案与域内参数副作用；恢复时同步 Worker 参数。不得仅恢复 Python 字典而留下支路状态或执行器参数不一致。
- 流体按其现有子步接受；热／制冷保留整控制段与适应步长试算的事务边界。事件在采样前还是采样后应用，以现有相应域行为及测试为准。
- 建立单一的资源释放路径：重复 close 安全，部分初始化失败也释放已创建执行器；避免基类和子类重复调用用户 finalize。
- API 控制预览增加内部会话方法，返回已声明脚本的预览结果；保持 HTTP 响应合同不变，预览仍不启用脚本或修改保存项目。
- 新公共层及协议采用明确类型；新增一个限定范围的 mypy 配置或等价门禁，不一次收紧整个历史引擎，也不用整文件忽略掩盖错误。

## 5. 数值、提交与失败处理

### 数值兼容

- 以既有测试的绝对／相对容差和独立守恒断言为准；本轮不放宽断言来适应重构。
- 基线对照保持变量键、单位、模块双哈希、事件语义、参数修订及已接受时间一致。运行 ID、墙钟时间和性能计时不作逐字节比较。
- 性能仅记录同一代表案例的实际变化；若出现稳定可复现的明显退化，则定位本轮新增拷贝、快照或 RPC。此轮不承诺未经测量的提速比例，也不扩大成性能专项。

### 提交节奏

一个工作包可以有“提取 → 迁移 → 验证”多个小提交，提交不得混入其他包的未验证工作。已有架构图整理先作为独立文档提交保存。

实施时从记录过的基线建立 `codex/architecture-refactor` 工作分支，基线修复、前端整理、会话整理分别保留可撤回的提交边界。推送该分支并建立面向 `master` 的 PR 触发当前仓库的 CI；若 PR #7 尚未合并，在 PR 中注明继承其基线，已有 PR 合并后再核对差异范围。推送仅用于验证与评审，合并另按用户指令处理。

### 遇到失败

1. 停在当前包定位失败，保留日志、输入和上一可用提交，不继续叠加依赖改动。
2. 能从代码或环境修复的问题直接修复并复跑受影响检查；需要改变物理算法、外部合同、兼容范围或产品行为时，先给出具体差异和选择再询问用户。
3. 相同失败在基线也出现时，记录独立复现并分类处理，不能借此删除测试或把最终验收写成通过。
4. 每包完成后写实际修改文件、测试命令、通过／失败状态及证据路径；最终更新架构图，保证说明与代码同步。
