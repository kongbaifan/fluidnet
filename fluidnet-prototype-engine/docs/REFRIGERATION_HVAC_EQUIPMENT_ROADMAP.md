# 制冷与暖通设备模型：现状、增补顺序与交付标准

核对日期：2026-11-05。依据当前工作树的可执行目录、设备实现、编译限制与验收记录；包含本地已实现但尚未提交的设备扩展。本页保留规划与能力边界；2026-11-05已按条目实施首版，当前实际交付、定向证据及未涵盖物理见[整体实施记录](EQUIPMENT_PROGRAM_DELIVERY.md)。不把首版范围扩大为厂家全工况模型。

主线：做可复用设备模型，通过参数、实际端口连接及工质配置组装系统。案例用于证明设备能够组合，不把固定案例编号、设备数量或控制脚本藏入设备实现。本轮不转为控制模板项目，不重新安排已取消的打包发版、真实外部联调、24小时专项和现场工程校核。

## 4. 项目标准：每个设备都必须按此交付

### 4.1 依据与实现选择

可执行合同优先：`models.py`及冻结`_module_schema_v1…v4.py`、`module_contracts.py`、各域编译器和设备实现；之后才是现行指南与日期明确的历史计划。当前SDK最高0.8.0不表示所有模块必须升级到0.8.0，也不表示所有域都支持该版本的全部能力。

- 仅尺寸、Kv、UA或曲线取值不同：优先参数/型号。
- 已有设备组合即可表达：组合定义固定子版本、公开端口/参数，不重复写算法。
- 作者接口可表达的新无储量关系：Python包，按适用域与能力声明。
- 新物理储量、真实端口焓或新联立未知量：明确内核/会话扩展，不能用Python累计JSON状态伪装物理储量。
- 制冷角色当前只开放Python等焓节流；其他制冷新设备可以先注册内置物理模型，不能承诺任意作者设备已开放。
- 湿空气/风水不接受普通域的新`net.pressure_drop`，也不接受现有水箱/困液/普通双侧换热器或分布水管热容；新增设备必须对具体目标执行域验收。

### 4.2 设备设计卡（编码前）

每项至少明确：模块ID/版本/运行类型、目标执行域与工质；端口方向/相态/回路、压力参考与连接限制；规范参数/显示单位/默认值来源/范围/runtime权限；物理方程与性能图来源；物理状态、派生量和接受累计量；零流/停机/反流/临界/超界行为；诊断code及实例/字段；旧模型和项目兼容方式；独立参考与组装验收场景。

规范单位使用绝压Pa、K、kg/s、J/kg、W，显示换算沿用 `canonical=(display-offset)×scale`。不得把摄氏温差重复偏移，把体积分数当高度百分比，或把电功率和轴功重复加入热账。未标定数据明确标为教学假设，不能由截图读数反推“已验证精度”。

### 4.3 分层验证

沿用[模块开发套件](MODULE_KIT.md)的L1–L4含义，不重命名层级：

| 层级 | 要验证的内容 | 内置与作者模块的执行方式 |
| --- | --- | --- |
| L1 合同 | 参数/端口/变量、单位、版本、合法与非法输入、域选择 | Pydantic/目录/编译校验；作者再含包加载及SDK能力 |
| L2 逻辑 | 设备函数的正确性、零值/极限、重复求值无副作用、接受状态约束 | 内置纯函数直接测；Python使用对应Runner/Worker协议，不机械给内置套Worker |
| L3 网络集成 | 真实联立求解、质量/能量账、状态接受/失败回滚、控制写入权限 | 任意ID、复制同类设备、不同拓扑与允许工质、冻结项目/报告、重启后复算 |
| L4 参考算例 | 解析解、独立计算或外部同条件数据 | 标明参考源与容差。独立数值检查不能写成厂家或倍思鹿等价；缺外部基准时明确未完成该外部对照 |

物理方程计算使用独立参考，不能复制实现公式生成预期值后当唯一证明。按设备量纲制定误差标准，复用引擎原压力/质量/热残差要求；不能为了通过新设备放宽既有求解门槛。累计量只在接受步推进，失败/缩步/重复候选不重复记账；保护在正确的最终候选边界检查，不能误拒绝尚未收敛的中间迭代。

### 4.4 使用流程、兼容与交付物

每项交付合同与实现、独立模型说明、recipe及规范项目、定向测试和证据。模型说明含公式、参数单位/来源、适用范围、诊断、已知限制。

必须走通：空白画布逐台插入 → 实际端口连线 → 参数预览应用 → 运行 → 实际ID结果/曲线 → 保存导出 → 新项目导入/重载复算 → 冻结报告。唯一界面基准1920×1080/DPR=1。只导入整套示例不能替代从空白组装的证明。

发布版本不可覆盖；旧schema解释、模块整数版本、源码/定义双哈希与项目固定快照分开维护。新物理语义用新模块ID或明确新版本；不偷偷改变旧字段含义，不为迁移重算覆盖历史哈希。源代码及数据变更核对相关生成物，仅更新预期变化并记录原因。

只运行本设备及受影响路径的定向测试、语法/ruff/mypy、相关合同与生成检查；不把全量pytest或全浏览器链当作每个小改动的反馈。全量验证当前按用户要求暂不运行，不预先写为通过。

## 5. 本轮采用的实施顺序（历史计划）

首先并行推进 **R01压缩机性能/包络、H01风侧三通/分支箱、H02风机停转与效率**。这批能增加设备层可用能力，接口相对清楚，避免把暖通储量或DX整个新执行路径混入一轮。

紧接着做 **R02一库多冷风机、H04板换工程化、H05压差旁通**；再分别设计 **R03中冷两级、R04泵供液融霜、H07闭式储热、H08膨胀罐、H09塔池**。R05/R06/R07属于真实制冷端口状态扩展链，先合同与独立物理基线再实现，不能跳过前置。

原盘点阶段只核对清单；后续用户已授权整体实施。各项首版交付与验收见[整体实施记录](EQUIPMENT_PROGRAM_DELIVERY.md)，历史三种设备证据仍保留于[上一批记录](REFRIGERATION_EQUIPMENT_EXPANSION.md)。
