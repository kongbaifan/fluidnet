# FluidNet：设备组网与运行仿真的完整实施计划

制定日期：2026-11-10。当前目标由用户明确为：**FluidNet 聚焦设备组网和运行仿真，把已有的建模、运行、调参、结果查看做稳定、做容易理解。**

本页是当前开发顺序和完成标准的统一入口。按普通任务逐项执行，不使用 `/goal`、自动目标推进或定时任务。本次完成的是计划编制；下文各阶段尚待按当前工作区执行和验收。

## 1. 最终要交付的使用体验

用户打开软件后，能够完成下面一条连续流程：

**打开或新建项目 → 从已有设备搭建系统 → 检查连接和参数 → 运行 → 修改一个参数并确认生效 → 查看系统响应 → 保存、重开并继续使用。**

普通使用者通过界面完成这些操作。需要自定义算法时仍可进入现有作者功能；制作新模块、编辑 Python 或 JSON 不作为使用已有设备的前置步骤。

本轮用四个问题判断改动是否有价值：

1. 用户能否找到设备、完成连接，并知道哪里没有接对？
2. 用户能否启动、暂停、单步、继续、停止，并知道计算进行到了哪里？
3. 用户能否知道改了什么、是否已应用、何时生效，以及为什么不能修改？
4. 用户能否知道结果属于哪个项目、哪次运行、哪个时刻，并解释参数变化后的响应？

保存与恢复贯穿上述流程。已确认保存的数据可靠性、真实结果和适用范围始终是完成条件。

### 阶段 2：运行与异常反馈

具体工作：

1. 逐项核对未运行、准备中、运行、暂停、正常结束、手动停止和失败的界面表现；复用现有状态合同，保证按钮可用性与后台状态一致。
2. 启动前检查必要配置。计算进行中显示实际仿真时刻与运行状态；初始化或求解较慢时给出明确反馈，不以静态成功提示代替结果。
3. 检查连续点击运行、快速暂停/继续、暂停后单步、停止时仍有请求返回等情况，确保命令不会作用于错误运行。
4. 明确仿真时长、输出间隔和实时/快速节奏的含义；数值求解高级参数保留在高级区域。
5. 运行失败或连接中断时保留最后接受的结果、草稿和诊断；说明可重试、需修改参数还是需重新运行。
6. 对持续仿真核对时间单调推进、暂停保持状态、单步推进和停止回执。已有快照续算单独显示其来源与支持条件。

交付：一致的运行控制和可处理的错误信息。所有展示均指向真实项目、运行及采样帧。

通过条件：支持的命令都收到可识别回执；暂停后状态不继续变化，停止确认后历史不继续伪增长；切项目后旧响应不能覆盖新项目；失败能够定位原因并保留可恢复的数据。

主要落点：`run-commands.js`、`project-run-state.js`、`workbench-refresh.js`；只有复现到服务端问题时才修改会话或运行管理代码。

### 阶段 3：调参与常用控制

具体工作：

1. 对常用设备明确区分输入草稿、已应用设置和运行采样值；给出单位、合法范围及运行时是否允许修改。
2. 保持现有预览与应用事务，核对取消、失败、重复提交以及请求期间继续编辑的行为；失败不得清空新草稿。
3. 运行中可修改的参数以后台确认和实际接受时刻为准；需要停止才能改的结构参数在操作前说明原因。
4. 控制器或脚本接管参数时显示控制者和正确调整入口。常用库温目标、回差、负荷及手动/自动操作复用已有能力；详细 PID 和脚本继续作为高级配置。
5. 依次验证 A 的阀门开度、B 的负荷与目标温度、C 的单库目标修改，观察对应设备和系统响应。
6. 核对曲线点表、百分比、毫米、温度和功率等显示单位，确保预览、保存和计算使用相同物理值。

交付：统一的参数含义与生效反馈，以及代表场景的常用控制入口。

通过条件：用户能回答“我改了什么、是否已应用、何时影响了运行”；非法输入被准确指出，原设置与草稿可恢复；成功应用后结果身份正确更新；控制接管有解释且不会被其他输入路径绕过。

主要落点：`device-application.js`、`device-panel.js`、`device-guide.js`、`cold-room-controls.js`、既有控制服务。

### 阶段 4：结果阅读与对照

具体工作：

1. 按设备用途选择默认读数：泵看流量/压升/功率，阀管看流量/压降，库房看当前与目标温度，机组看状态/能力/功率；完整变量表保留为进一步查看入口。
2. 明确当前结果、历史结果、参数已改变后的过期结果，以及尚无采样的区别。缺失值显示缺失，不能补零或演示值。
3. 画布与设备窗口共用现有完整采样帧并标明时间；曲线按实际历史采样展示，不把两者的时刻混为一谈。
4. 核对关键读数加入曲线、变量搜索、单位、坐标和图例。对历史说明提到的旧设备包装缺少观察按钮的问题，先复现，再补实际缺口。
5. 复用现有两次运行比较与报告能力，让用户能查看调参前后区别。比较记录必须带运行身份和参数来源，缺少信息时明确提示。
6. 失败提示说明是计算失败、状态越界还是能力不足，并能回到相关设备或设置。

交付：代表场景的默认结果视图、可追溯曲线和调参前后对照流程。

通过条件：通过界面能够解释 A 调阀后的支路变化、B 增载后的库温/机组响应、C 不同库的状态；曲线、设备读数和导出使用正确运行；参数更新后旧结果不会冒充新结果。

主要落点：`device-panel.js`、`canvas-observations.js`、`run-results-view.js`、已有观察变量和报告服务。

### 阶段 5：保存、重开与复用

具体工作：

1. 整理项目保存、整个工作区保存和结果归档的提示；常规使用优先让用户明确当前项目是否保存成功。

3. 关闭页面并重新打开、重启服务后恢复项目，核对设备、连接、参数、工质、模块版本、控制配置和曲线绑定。

## 设备缺口怎样进入开发队列

先在搭建中记录具体阻断，再决定修复方式。每条记录至少包含：使用场景、所需设备/过程、已有模块、实际限制、影响、能否组合解决、优先级、完成标准和证据位置。

处理顺序：

1. **已支持但难用**：补说明、参数入口、错误定位或默认面板。
2. **能由现有模块组合**：补设备组、参数映射或可编辑模板。
3. **现有模块有明确缺陷**：修复问题并验证原使用场景。
4. **缺少必要物理或接口**：先限定所需设备的输入、输出、状态和范围，再开发独立模型，并验证其进入系统后的行为。

影响当前选定系统搭建或结果正确性的缺口优先；可用且不阻断的增强项后置。各模块的独立验证、适用范围和与系统连接的正确性分别记录，不能由一个示例运行成功推断全部工况可用。
