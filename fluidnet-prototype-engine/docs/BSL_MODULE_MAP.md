## 一、口径说明

- **34 个模块**：`AlgModule` 下共 35 个目录，其中 34 个是模块目录（`Zbackup` 为空目录，不计入），对应 34 个互不相同的 `ModuleOneID(...)`（逐个提取后去重计数为 34）。表内「倍思鹿模块」列与目录名严格一致。
- **中英别名**：23 个模块同时有中文名与英文名源码（如 `压缩机` / `CPSRSCREW`），两者是同一模块的两份根 `.cpp`。中文名是工程内显示名，英文名是早期命名。**两份并不保证逐字相同**：`压缩机` 这一对相差 14 行，含 `MuBiaoPre` 判据 0.1/0.2 的差异、英文版多出的 `Opening<0.1` 钳位、以及写死的 `CPSRSCREW.exe` 名。这说明包内是「多版本快照」，本文一律用中文目录名，英文名只在必要处标注。
- **运行与设计变体**：每个模块都有 `code/<模块>_Run.cpp`（运行函数）与 `code/<模块>_Design.cpp`（设计函数），由模块编辑器拼装成根 `.cpp`（含 `main()`）。根目录的 `_D.cpp` 是对应的设计变体可执行源码；`_R.cpp` 是另一套链接路径的变体。因此「一个模块」在磁盘上是 2～6 个 `.cpp`，不是 1 个，且变体之间已出现行为分叉。
- **11 个模块没有英文名根 `.cpp` 构建变体**：`MOS管`、`中间冷却器`、`二极管`、`二极管反`、`关断器`、`比较器`、`泵曲线法`、`电位器`、`直流电机`、`罐体立式`、`霍尔电流`。它们的物理代码直接写在中文名根 `.cpp` 里（`中间冷却器.cpp` 1017 行、`罐体立式.cpp` 1055 行），并非「没有根文件」。其余 23 个模块有 6 个根 `.cpp`（中文名 2 个 + 英文名 4 个）。
- **46 个 `*_R.cpp` 不可直接编译**：23 个模块 × 2 个 `_R` 变体 = 46 个。`_R` 变体 `#include "../../Lib/FudPhyLink.h"` 并链接 `Lib\*.lib`，而包内只有 `Lib\debug\`（`FudPhyLink.h`、`ModuleAPILink.h`、`NodeAPILink.h`），发布路径的头文件与库不存在；非 `_R` 变体引用 `Lib/debug/`，才能编译。`_R` 只作为「同一逻辑的 release 版」参照。
- **`.Modu` / `.pjt` 加密**：34 个 `.Modu`（实测 4.3 KB～111 KB）是 base64 文本密文（首 64 字节形如 `VFeLG8qhDvUuiwUstJZ00BX-d-…`），无法解出端口、参数、变量名。**只作行为参考，不复制源码，也不据此反推合同。**
- **不承诺 1:1 覆盖**：FluidNet 的内置模型是「声明式合同 + 全网方程」，倍思鹿是「模块 EXE + NET DLL 关系调用」。同名设备在两边的自由度、状态量、边界条件都不同；本矩阵给的是**可验收的落点**，不是逐行等价物。
- **判定口径**：「现有能力」只写 `catalog.py` / `refrigeration/` 中已注册、且有测试或验收痕迹的模型；「缺失能力」写需要新代码或合同变更的部分；「不移植」写明确拒绝或域外。
- 表内序号按物理族归并、组内按目录序，**不是**目录枚举顺序。
- **人日口径**：一名熟悉两端代码的工程师，含算例脚本、文档与自测，不含硬件联调、不含等待真实设备数据的时间；电气 11 项按「不移植」记 0。
- **优先级口径**：P0 = M1 内必须完成且已有现成模型可对齐；P1 = 设备面补齐；P2 = 需要新物理或语义重写；P3 = 控制组态，可随时做；D 类不给优先级。
- **快照说明**：本矩阵核对期间工作副本正被并行修改。`modules/check_valve`、`modules/fan_coil_unit` 于 2026-10-22 15:34–15:35 新增，`modules/pipe_fitting` 同时被改动；本文按 **15:40 的文件系统**记录这两个包，但**没有运行**它们的测试，验收结论仍以主表最后一列为准。若后续包被回退，对应行按「无此包」回读。

### P0 建议（4 个）

1. **管道通用**（A，1 人日）——管网骨架，`pipe` 已具备 Darcy/热容/散热，先做同工况压降对照，为后续所有设备建立误差基线。
2. **压缩机**（C，4 人日）——制冷回路的核心与最大风险点，`refrigerant_compressor` 与 `condensing_unit` 两套实现都已存在，先对齐额定点与载量阶跃，避免在错误的工作点上讨论其他设备。
3. **蒸发式冷凝器**（C，3 人日）——排热边界，决定 T_cond 与整站能量闭合；`evaporative_condenser` 的湿球近似是已知简化，越早暴露偏差越好。
4. **罐体卧式**（C，5 人日）——贮液器是制冷站拓扑的必需容器，`hp_receiver` 已有 (M,U)→p/液位；先做单容器存量与液位的 2 h 演化，再谈多容器组网。

理由：这 4 个里 1 个建立单相管网基线，3 个组成「压缩—冷凝—节流—贮液」最小可运行制冷回路，且**全部有现成模型**，M1 的产出是「口径确认 + 误差数据」，不是新物理。未入选但接近 P0 的：蒸发器（6 人日，需先确认满液式换热关系）、截止阀（2 人日，属管网域，M2 再并入）。

### M1 垂直切片（已交付，2026-10-22）

本表之外另交付了 6 个可直接插拔的 Python 模块包，用于先把「模块包 → 求解 → 帧变量」的最小闭环跑通。

**P0 批次（3 个包，覆盖 4 个倍思鹿模块）**

- `modules/pipe_fitting`（弯管/异径管/三通/进出口局部阻力，对应本表 #2/#3）；K→Kv 等效已实测（`d=0.05, K=0.9 → 105.37 m³/h`）。

**P1 批次（3 个包，对应 #8/#9/#13）**

- `modules/cooling_tower`（#13）：水侧管网 + 逆流 ε-NTU（湿球近似），干空气显热模型，输出逼近度/出风温度/换热量。

## 四、关键说明

### 4.1 为什么不做 1:1 翻译

1. **求解器黑盒**。倍思鹿模块只调用 `PIPECV` / `PUMPCV` / `VALVECV_SHUT` / `Netlink_Pipe` / `Netlink_Pump` / `Netlink_Valve` / `Netlink_Cpsr` / `Netlink_Check` 等入口，把阻力系数 `R`、流通能力 `CV`、惯性与网络组装交给宿主 DLL（`CommonLib`、`FudPhyLink.lib`、`ModuleAPILink.lib`）。源码给的是**调用参数**，不是方程；`CV`/`R` 的内部定义无法从包里恢复。FluidNet 用 SciPy 组装全网方程（支路定义、并行粒度与 BASELU_COMPARISON 第 44–49 行一致），两边不是同一层抽象。
2. **两相边界**。倍思鹿把两相闪蒸放在模块内部（`BKT_CORE`、`PTT_BKT`、`FUD_SATP`、`FUD_PH`），端口仍按单相传递；FluidNet 的合同是「管网流动只支持与回路边界一致的单相，两相只在设备内部查询」（README 与 ALGORITHM「后续状态算法」）。逐行翻译会把两相塞进支路，直接违反 `PHASE_UNSUPPORTED`。
3. **加密元数据**。`.Modu` 与 `.pjt` 是密文，端口名、参数默认值、变量表都无法读取；不能据此生成 FluidNet 的 `ModuleDefinition`。任何「按倍思鹿参数表 1:1 复刻」的说法都缺证据。
4. **单相网络限制**。FluidNet 当前内置 7 类（`source`/`junction`/`pump`/`valve`/`pipe`/`exchanger`/`tank`）+ 2 个热力节点 + 3 个冷库 A 设备 + 10 个制冷站设备 = 22 个模型；没有闭式两相罐、没有两相支路、没有管道惯性与水锤（ALGORITHM 明确列入「未实现」）。这决定了 8 个 C 类只能进制冷域，8 个 B 类只能靠 Python 模块或内核小改补。
5. **证据强度不均**。46 个 `_R.cpp` 引用不存在的发布路径；11 个模块没有独立英文构建变体；`直流电机` 的 `_Run.cpp` 是 0 字节、`二极管` 只有 1 行 `NetPower_Check(0, R, H,0);`。这些文件只能证明「模块存在」，不能证明「算法完整」。

### 4.2 应作为「语义参考」而非代码来源的模块

- **容器族**（罐体卧式、罐体立式、冷库库房、中间冷却器）：可参考**分层取液与位置压力修正**的写法（`IM0_PRE = BKT_PRE + BKT_D·9.8·BKT_SH/4/1e6` 这类按液位分段的端口压力），但实现必须落在 `saturated_vessel` 的 (M,U) 反求路径上，不能照搬 `BKT_*` 调用。
- **冷却塔**：`FANRUN ≥ 0.5` 分支把出口比焓**硬编码为 134.1818 kJ/kg**（≈32 °C 水），风机停转时才做等焓旁通。这是演示级行为，只能取「逼近度」语义，不能作精度基准。
- **热力膨胀阀**：`CP = 0.02005·√ρ + 6.34·CV`、`AV = (1.9 + 0.28·TC)·1e-6`、`M_PRE = CV·m²/CP²/AV²` 是经验拟合式，可作为过热度—开度趋势参考，不能当物性推导。
- **管壳式换热器**：壳侧用 `BKT` 容器 + 管程多回路拼装，属于「设备内自洽」写法；FluidNet 必须拆成 `exchanger` + 容器两个合同对象。
- **电力与信号 13 项**：只保留**联锁语义**（如风机盘管控制的阈值启停、比较器的模拟量→数字量），其余不进入代码来源。
- **单相阻力件**（管道通用、弯管、异径管、截止阀、泵曲线法）：关系式是标准工程式（Darcy–Weisbach、K 系数、Kv、相似律），FluidNet 已有实现更完整，**不需要**从倍思鹿源码取任何公式。

### 4.3 与 BASELU_COMPARISON.md 的关系

- 本文是**模块级细化**：那份文档回答「两边能力差在哪」，本文回答「34 个模块各自落到哪一行、缺什么、怎么验收」。
- 不推翻既有结论：求解器黑盒、两相管网未支持、加密与部署/调试差距、单相网络限制，本文全部沿用。
- 需要更新的**一处事实**：BASELU_COMPARISON 第 23 行写「7 类内置模型」，那是 2026-10-15 基线；当前 `catalog.py` 已是 22 个模型（含冷库 A 与制冷站 B）。本文按当前代码判定「现有能力」，该行的历史结论不改写，只在此注明增量。
- 本文的「落点」不等于「已实现」：标注为内置模型的条目仍需各自的验收算例（见主表最后一列）才可宣称覆盖。

## 五、建议实施顺序

### M1 基线对齐（P0，约 13 人日）

范围：管道通用、压缩机、蒸发式冷凝器、罐体卧式。

验收标准：
1. 4 个器件各有 1 个可复跑的算例脚本或项目文件，工质、边界、初值、容差写清。
2. 每个算例至少有一个**独立于引擎**的参考（手算关系式或直接调用 PropsSI），相对差写入文档；不做「精度优于倍思鹿」的结论。
3. 制冷回路算例闭合：质量守恒、能量残差 < 1e-3 W，`pressure_ratio` / 液位在模型适用带内。
4. 明确记录 4 个器件的**不等价项**（如倍思鹿端口数、卧式几何、风机曲线缺失），写进本文对应行。

### M2 设备面扩展（P1，约 24 人日）

范围：弯管、异径管、截止阀、泵曲线法、风机、管壳式换热器、蒸发器、罐体立式。

验收标准：
1. 新增/扩展模型有回归测试（单器件 + 一个组网工况），不进全量 pytest 也可单独运行。
2. 制冷站与单相管网两套示例均可运行，且**没有**引入两相支路或闭式罐到通用管网。
3. `pipe_fitting` 的 K 表覆盖弯头与异径管，参数化后仍保持单位合同与版本快照。
4. 每个 P1 条目在本文表格里从「缺失」改为「已实现 + 验收算例路径」。

### M3 边界与语义参考（P2/P3，约 42.5 人日）

范围：毛细节流阀、止回阀、泵迭代法、冷却塔、风机盘管、中间冷却器、冷库库房、容积型源头、热力膨胀阀、比较器、风机盘管控制。

验收标准：
1. 每项给出**二值结论**：「已实现（附算例）」或「明确拒绝（附原因与合同报错码）」；不允许停留在「部分支持」。
2. 止回阀若无法给出稳定的单向约束，保持 README 的拒绝行为并在本文记录，不用「近似单向阀」蒙混。
3. 冷却塔、热力膨胀阀、容器族的「语义参考」部分单独成节，注明哪些是倍思鹿的工程近似（尤其 134.1818 kJ/kg 硬编码）。
4. 电气 11 项维持「不移植」，只在需要联锁演示时以控制脚本表达。
