## 最先处理的具体问题

### D01：旧原型设备入口与真实可计算能力不一致（P1，已复现）

当前模块库仍包含 `check`（止回阀）、`sensor`（流量计）、`pid`（PID 控制器）、`refprop`（物性测试）四个未注册为可计算模型的旧入口。卡片中的描述、编辑和加入项目操作没有统一表达该限制。把旧 `check` 放入规范化输入时，真实后端返回“项目使用的模块 check (check) 尚未注册求解算法”。

这不是后端没有止回阀或 PID 能力：可执行的止回阀模块、项目测点和项目 PID 已有实现。问题是旧入口与当前能力共存，用户容易选错。

建议：根据目录与模块合同生成可执行标记；旧对象保留为迁移/参考入口，加入项目之前说明限制；提供当前止回阀、理想测点和控制页的替代路径。验收应从界面选择设备并运行，不能只检查卡片存在。

证据：`model-entry-probes.json`；代码：`backend/fn_engine/bridge.py:108`、`frontend/studio.js:1532`。

### D02：内置设备“算法”编辑页容易被理解为真实算法入口（P1，行为已复验）

调节阀的内置设备编辑页显示可编辑的 Python 运行代码、公共代码、设计函数和“保存定义”。当前执行的是内置模型，编辑这些代码不会改变其计算方程。隔离复验把内置阀门的运行文本改成必定抛错的代码，求解仍成功，所有变量一致；阀流量前后均为 `3.5826766415095452 kg/s`。

后端按内置合同运行是当前设计边界，问题是界面的任务表达。建议在页面主位置写清“内置算法由引擎执行；此文本用于说明/预览”，将实际不可执行部分设为只读或提供“创建可执行 Python 模块”路径。Python 模块继续保留验证与版本发布流程。

证据：`builtin-code-probes.json`、`module-code-1920.png`；代码：`frontend/module-editor-view.js:90`、`backend/fn_engine/bridge.py:134`。

### D03：六库示例先渲染，后适应画布，首次画面不完整（P2，已复现）

1920×1080 下从项目示例创建六库自动温控，当前页有 21 台设备，首次只完整显示 11 台。首次 SVG 的 viewBox 是 `-35 -5 1140 510`；点击“适应画布”后变为 `87.6 77 1134.8 1039`，21 台均完整显示。

创建流程调用 `openProject()` 渲染后才调用只修改画布状态的 `fitNetwork()`，没有同步刷新 SVG。建议在渲染前完成布局，或者拟合后明确刷新并保存一致的视图状态。

证据：`fit-probes.json`、`six-room-before-fit.png`、`six-room-after-fit.png`；代码：`frontend/cold-storage.js:147`、`frontend/studio.js:1247`。

### D04：保存服务的晚回执缺少工作区归属保护（P1，服务层隔离复现）

`workspace-storage.js` 会忽略已经被替换的工作区的晚回执，但其下游 `project-services.js` 在返回回执前已经直接修改 `ui.state()` 的修订、项目修订和已保存参数键。

隔离调用复现：旧工作区保存尚未结束时替换工作区；旧回执返回后，新工作区的 `workspaceRevision` 从 99 变为 1，项目修订与 saved keys 也被改为旧项目的数据。此复现确认元信息跨对象写入，不表示已复现工程内容被覆盖；真实界面的多种替换/并发保存组合还需专项验证。

建议给服务层保存/载入添加工作区身份或代次票据，区分服务端最新修订与当前草稿所属修订，过期回执不得写入当前对象。验收需覆盖保存中恢复、导入、项目保存和断连重连。

证据：`service-probes.json`；代码：`frontend/project-services.js:37`、`frontend/workspace-storage.js:94`。

### D05：通用 HTTP 请求没有自身的超时与取消路径（P1，代码确认与延迟复验）

公共 `request()` 直接等待 `fetch()` 与 `response.json()`，没有为每个请求设置到期取消。同步运行的五分钟轮询上限在循环两次请求之间检查，无法中断一次长期没有返回的请求。保存等待期间也没有用户可用的取消按钮。

延迟保存复验确认界面持续显示“正在保存…”，恢复响应后能保存成功；这只是延迟场景，不把 2.5 秒正常等待本身定义为超时缺陷。风险来自无期限等待的结构。应给请求设置有区分的期限，并为保存、初始化和运行命令提供可恢复状态；对写操作先核对回执与修订，避免盲目自动重发。非 JSON 错误响应也应保留 HTTP 状态和可读诊断。

证据：`defect-probes.json`；代码：`frontend/engine-client.js:95`、`frontend/engine-client.js:457`。

### D06：重要运行档案没有固定保留机制（P2，现行策略确认）

后端自动保留最近 20 次结束运行；更早的普通运行会在 `_prune()` 中删除。运行页标题的悬浮提示说明了此政策，但主界面提示较弱，没有固定重要档案的操作。批量结果有独立快照，不应与普通运行的留存方式混同。

建议提供固定保留、命名、项目归档和容量查看，明确最近窗口、全程抽稀与完整采样的差别。重要工程试验不应只依赖“最近 20 次”。

代码：`backend/fn_engine/storage.py:224`、`frontend/run-results-view.js:20`。

## 底层算法的判断与后续验证

本轮定向检查与 25 次代表运行没有发现整体求解错误。现有实现已包含以下能力，应保留并继续验证，而非登记为缺失：

- 自动选择稠密/稀疏水力求解、解析/混合 Jacobian 与有限次数回退，仍使用同一压力/质量残差门；
- 串联压缩与依赖安全的分块求解，失败时保守退回原求解路径；
- 一阶隐式推进、整步/两个半步局部误差估计、按 kg/J/K 区分误差尺度与事件边界截断；
- 试算/接受状态分离、拒绝步回滚、参数原子写入、Python Worker 隔离；
- 单步和暂停保持会话、JSON 会话快照、代码与依赖指纹、恢复等价检查；
- 守恒/残差与冻结运行解释，未知采样不补零。
