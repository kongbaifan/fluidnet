# RF-0：首类制冷设备扩展接口与可行性验证

日期：2026-10-30。承接 [PF-0/PF-1](PLATFORM_AUTHORING_ACCEPTANCE.md)。本阶段验证公共 SDK 用户算法、真实 Worker、制冷站方程及全段接受的组合；正式模块合同、公共编译和作者界面留给 RF-1 至 RF-4。

## 结论与范围

已有 Worker 与候选状态事务可以复用。试验将一台内置等焓节流阀替换为独立进程中的 Python 算法，输出进入原制冷站的容器质量和能量方程；没有复制制冷站物理模型，也没有更改公共编译器的设备限制。

两个原计划假设经源码核对后明确如下：

- **纯集总制冷站没有独立稳态求解入口**，`solve_station_steady` 返回 `REFRIGERATION_DYNAMIC_REQUIRED`。本轮比较固定候选状态上的设备/全站求值和动态积分，固定工作点求值不标成稳态收敛。新增完整制冷站稳态求解器不属于设备扩展的隐含交付。
- **schema 3 的适用执行域冻结为 `fluid`**。不能直接给旧合同添加制冷域并改变其历史规范化/哈希；RF-1 应增加新合同解析器，保留 schema 1/2/3 的语义。

原型入口是 [scripts/rf0_probe.py](../scripts/rf0_probe.py)，作者源码是 [rf0_throttle.py](../examples/refrigeration_extensions/rf0_throttle.py)。它们是实验程序；正常项目验证、API 运行及模块发布没有开放制冷 Python 设备。直接把实验项目交给公共编译器仍在运行前拒绝。

## 首类角色的语义

选择 `refrigeration.isenthalpic_throttle.v1` 作为建议角色名。仅连接上游饱和容器液相出口和合法的另一压力等级，保留现有回路工质、端口方向及容器取相检查。

| 方向 | 数据 | 单位与含义 |
| --- | --- | --- |
| 平台 → 作者 | 上/下游压力 | 绝压 Pa，来自同一次候选 `(M,U,T)` 状态 |
| 平台 → 作者 | 上游液体温度、比焓、密度 | K、J/kg、kg/m³；由该次候选上游压力的饱和液态物性得到 |
| 平台 → 作者 | 工质、开度、额定 Kv | 工质由所在回路冻结；开度 0–1；Kv 沿用已有工程定义 m³/h |
| 平台 → 作者 | 运行/实例/请求/接受段身份，候选时刻与最近接受时刻 | 候选时刻是当前试算终点；最近接受时刻不随牛顿探测或失败试算推进 |
| 作者 → 平台 | 有效 Kv、质量流量 | 有效 Kv 在 0 到额定 Kv 之间；质量流量为有限非负 kg/s；必须与声明的 Kv 关系一致 |
| 平台自行生成 | 两端流量、流股比焓、下游闪发状态、容器质量/能量通量 | 出口与入口等焓，两容器记相反的质量/能量流；作者不能直接写容器状态或重复记账 |

首个作者模块实现 `effective_Kv = rated_Kv × opening`，并通过公共 `fn_sdk.ModuleContext` 读取端口、参数和提交受管理观察状态，不导入引擎设备函数。独立参考关系为：

```text
m = effective_Kv / 3600 × sqrt(1000 × rho_liquid × max(p_in − p_out, 0) / 100000)
```

无正向压差或零开度时流量为零；返回布尔值、字符串、非有限值、负值、超额定值或与有效 Kv 不一致的流量都会失败。下游闪发仅用来确定流股状态；不开放管内两相压降、过热度自调、壅塞或设备独立物理储量。

## 试验运输方式与正式合同建议

RF-0 使用 schema 2 / SDK 0.6.0 的已有端口、变量和事务消息作为实验运输载体：`evaluate` 只返回两项规定变量，不注册水力通路；专用适配器验证结果并进入制冷站流股账。采用 schema 2 不意味着旧 SDK 正式支持制冷设备角色。

RF-1 的建议落点如下，均尚未成为可调用的公共接口：

1. 新增 **schema 4** 和 **SDK API 0.7.0**；保留旧版本解析和哈希。新字段显式声明制冷角色与版本，适用域包含 `refrigeration`。不能靠模块 ID、名称或把 `solver_model` 改成内置模型来获得权限。
2. 在公共 SDK 增加有类型的制冷输入/输出接口以及 `refrigeration.throttle.v1` 能力协商。正式流量响应从独立字段返回，替代 RF-0 的 `ctx.var` 实验运输方式；缺能力、错单位或未知角色在执行前拒绝。
3. 按声明的角色复用压力等级、取相及回路验证，接入原有 Worker、版本、诊断和发布服务；不建立第二套模块仓库。
4. `thermal`、`cold_store`、`coupled`、湿空气及组合适用性分别判断。首批只开放已验收的纯制冷站角色。

## 候选与接受事务

实验沿用制冷站“输出/控制/日程边界之间的整段接受”，步骤如下：

1. 开始接受段，冻结控制、参数、物理状态和已接受模块状态，生成唯一段身份。
2. 每次牛顿求值/差分探测，通过真实 Worker 求解同一候选状态上的阀门。`evaluate` 得到状态副本；其写入不会提升受管理状态。
3. 数值失败可按既有固定步机制缩步。只有通过容器检查的内部子步进入候选积分账；失败尝试不累计质量，也不调用作者提交。
4. 整段物理计算成功后，使用最终端口状态调用 `prepare_step`。收集候选状态，验证版本、双哈希、基础修订、段身份以及完整候选结果帧。
5. 父进程在没有 RPC/用户回调的接受点提升模块状态。物理、控制、日程、参数修订和时间处在同一回滚范围内；准备失败时一起退回段起点，已确认的外部参数命令仍保留。
6. Worker 同步放在父进程接受之后。同步失败保留已经接受的新状态及结果帧，并停止执行，不重复该段。重复同步不重复累计，重复提升及过期候选拒绝。

实验作者只记录接受段次数及末次接受时刻。`transferred_mass_kg` 由平台按真正接受的隐式子步流量积分；不会用最后一个端点流量乘整个接受段长度冒充积分。RF-2 若向作者开放累计观察量，需要提供已接受积分或可回滚的候选链。

原型覆盖固定步失败缩步；**自适应步加倍保持拒绝**，待 RF-2 验证整步、两个半步、全段回滚与作者状态的关系。错误 Worker 关闭；不承诺任意 Python 外部副作用回滚或跨服务重启续算。

## 性能预算与测量

测量前固定 [预算文件](platform-extension/rf0-performance-budget.json)，配置为完整 B `station_case`：五个 PID 加上层控制脚本、替换一台 `EV1`，仿真 60 s、输出步长 10 s。内置版/Python 版各运行 5 个独立 Python 进程并交替次序；工作点求值每次预热 2 次、记录 7 次。数值线程固定为 1。该短案例预算用于判断接入可行性，不能外推为任意规模的性能保证。

| 指标 | 预先固定的门槛 |
| --- | --- |
| 初始化中位数增量 | ≤ 3 s |
| 工作点求值中位数增量 | ≤ 5 ms |
| 60 s 动态耗时中位数增量 | ≤ `max(0.5 s, 内置耗时 × 50%)`；绝对下限避免极短运行的比例失真 |
| 总进程峰值采样工作集增量 | ≤ 192 MiB；按 25 ms 间隔采样父进程和所有 Worker |
| 迭代与资源 | 两版牛顿迭代次数一致；全部 Worker 回收；所有样本使用相同源码哈希 |

同时记录真实 RPC 动作数（含显式初始化、参数更新、求值、准备、同步和结束）、最终容器质量/内能、库温、全站残差。测量程序为 [profile_rf0.py](../scripts/profile_rf0.py)，最终数据见 [RF-0 验证索引](platform-extension/results/rf0-validation.json)。

本机最终 5 次独立样本的中位数：

| 指标 | 内置版 | Python 版 | 增量 |
| --- | ---: | ---: | ---: |
| 初始化 | 0.674 s | 1.340 s | 0.666 s |
| 固定工作点求值 | 0.152 ms | 0.608 ms | 0.456 ms |
| 60 s 仿真动态计算 | 28.163 ms | 60.684 ms | 32.522 ms |
| 总进程峰值采样工作集 | 166.234 MiB | 207.363 MiB | 41.129 MiB |
| 牛顿迭代次数 | 12 | 12 | 0 |

短案例的动态耗时约为原来的 2.15 倍，绝对增量为 32.5 ms，满足本次固定的短案例预算；不据此宣称多设备或长仿真开销相同。所有样本最终容器质量、内能及库温与内置版完全一致；两回路质量残差为零，全程能量残差约 0.000628 J。Python 阀实际执行 59 次 RPC：初始化 1、求值 40、准备 6、同步 6、参数更新 5、结束 1；两版上层控制脚本均为 8 次 RPC。
