# MOD-B2：v1 合同与后续扩展决策

日期：2026-10-23。代码基线：`98dadd52ff728af366ef973579894e0000a70eb0`；本轮补充见 M0 基线包。此决策固定当前行为，后续接口没有因此成为已实现能力。

## 1. 兼容对象与固定样例

`tests/fixtures/module-system/v1-snapshots.json` 保存十个已发布种子包的完整 v1 定义、源码和两类预期哈希（包括止回阀两个整数版本），另有单阀、四实例串联和双通路三个完整项目快照。哈希来自改造前的基线代码，不在测试中用当前实现重新生成预期值。

样例是历史输入，不能因生产模型增加字段而批量重写或重新计算预期哈希。新合同在 R0/R1 等交付点追加自己的样例集合，原集合继续运行。种子包内容变更必须使用明确的新版本和对应发布流程，不能用更新本文件掩盖旧版本漂移。

## 2. 两类哈希的精确口径

- `content_hash`：`module_source()` 得到的运行源码按 UTF-8 编码后取 SHA-256。源码是字符串列表时先按 `\n` 连接。包加载的文本换行遵循现有 `read_text()` 行为；设计源码不属于这个哈希。
- `definition_hash`：现有模型 `model_dump(mode="json")`，只排除 `content_hash`、`definition_hash`、`package_path`。对所有字典/列表递归处理，将整数值浮点数转换为整数；再按 `ensure_ascii=False`、`sort_keys=True`、`separators=(",", ":")`、`allow_nan=False` 序列化，UTF-8 编码后取 SHA-256。
- 定义哈希包含运行/设计源码、合同和默认解释。v1 不能因新增当前模型字段而改变这个输入集合。嵌套的参数/端口/通路/单位等默认解释同样属于 v1，不能只冻结最外层字段。
- 路径及哈希字段本身不进入定义哈希；参数、源码或有效合同变更应改变对应哈希。合同中的非有限数字拒绝序列化。

S2 已按 schema 分派冻结解析/规范化。若新能力改变字段含义、默认解释或规范化输入，则使用新 schema；不把 v1 对象自动补成新合同后重新保存。模块整数版本、SDK API 版本、状态合同版本与 schema 版本分开管理。

## 3. SDK 和执行路径边界

公共 SDK 采用计划中的 `backend/fn_sdk/`，和现有工程共同安装，暂不建立独立发行仓库。公开类型和关系构建器不得依赖引擎进程管理，不通过导入 SDK 启动 Worker 或加载 SciPy/CoolProp。可选物性服务在调用时再获取。具体签名由 S0 冻结，能力字段和版本拒绝行为由 S2 实现。

v1 的 `initialize/evaluate/commit_step/finalize` 入口、现有 `heat_w` 路径和保存源码继续有效；新热回调需显式能力声明。状态事务改造须用旧入口适配，并通过 T4 故障门；不能把此处的兼容约定理解为当前已实现全步回滚。

模块作者可恢复的状态范围限定为 JSON 对象形式的 `ctx.state`；任意 `self`、全局变量、外部 IO 或随机外部状态不属于恢复合同。当前实现没有完成新状态限值和有限值门禁，T0/T1 冻结并实现字节/深度/容器限值、兼容诊断及恢复协议。引擎 PID/脚本/参数状态另按计划第 5 节事务清单管理，具体协议待 T0；跨服务重启续算和跨模块版本状态迁移不在本轮范围。

## 4. 指标与验证层次

- `WorkerProcess._request` 一次实际调用计一次 RPC；批量请求按分片计 RPC，items 数另计模块 evaluate 请求数。初始化、参数写入和提交分别列 action；关闭时的直接管道写入不混入这个计数。
- 帧内 `solve_counters.residual_calls` 是既有真实水力残差调用口径；SciPy `nfev`/旧 `iterations` 不替代它。已接受帧上的计数不能冒充所有失败试算的总计数。
- M0 场景检查真实网络残差、有限结果、独立 Kv 公式和接受步质量账本。风机盘管及双侧热网络的回放是当前行为基线，不能代替 H6 的独立 ε–NTU/最终状态热回调验收；当前未新增外部标定证据。
- 存量种子包、用户保存版本、基准故障样例分开管理；故障注入只存在于独立的项目快照中，不覆盖种子源码或发布目录。
