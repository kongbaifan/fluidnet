## 1. 测量方法

每一轮都在**新进程**里依次测四类 Worker（每类 3 次，两轮共 6 个样本，取中位数）：

| 类别 | 首个动作 | 说明 |
| --- | --- | --- |
| control | `control_initialize` | 控制脚本 Worker，不做物性查询 |
| module | `initialize` + `evaluate` + `commit_step` | 普通 Python 模块（programmable_valve），试算端口自带密度/黏度，evaluate 不触发物性查询 |
| property | 同上，另在 evaluate 里调用 `ctx.fluid.state_pt` | 物性模块 Worker，首次 evaluate 即首次物性 |
| batch | `action=batch`（4 个子项） | 批量 Worker |

进程层另外测解释器启动（`python -c pass`）、`import fn_engine.worker` 墙钟和 `-X importtime` 分解。

## 2. 基线实测（v0.5.0）

### 2.1 进程层

| 项 | 中位数 |
| --- | ---: |
| 解释器 + 进程启动（`python -c pass`） | 0.083 s |
| `import fn_engine.worker` 整体墙钟 | 2.196 s |
| 其中 import-only（扣除解释器） | 2.113 s |

`-X importtime` 累计耗时排序：`fn_engine 2.199 s`（其中 `CoolProp 1.500 s`、`pydantic 0.222 s`）。
也就是说，Worker 启动的绝大部分是 **import**，而 import 里最大一块是物性库 CoolProp。

### 2.2 Worker 层（6 样本中位）

| 类别 | 首次响应（含 spawn+import+initialize） | 首次 evaluate | 首次 commit | 首次物性 | 首个成功步 |
| --- | ---: | ---: | ---: | ---: | ---: |
| control | 2.258 s | 0.0003 s（control_step） | — | — | 2.258 s |
| module | 2.212 s | 0.0008 s | 0.0004 s | — | 2.213 s |
| property | 2.144 s | 0.0024 s | 0.0004 s | 0.0024 s | 2.147 s |
| batch | 2.234 s | 0.0009 s（4 项批量） | — | — | 2.235 s |

### 2.3 首个成功时间步（新进程内 compile→solve）

| 网络 | 进程墙钟 | 其中 solve | 说明 |
| --- | ---: | ---: | --- |
| series 30 实例、无 Python 模块 | 3.739 / 3.507 s（两轮） | 0.063 / 0.070 s | 进程墙钟主要由解释器+import 构成 |
| series 30 实例、25% Python 模块（7 个 Worker） | 5.734 / 5.878 s | 2.263 / 2.376 s | 每个 Python 实例都要启动一个 Worker |

## 3. 结论与 W1 切入点

1. v0.5.0 的 Worker 首次可用时间约 **2.1–2.3 s**，其中 **~2.1 s 是 import**（CoolProp ≈1.5 s），
   协议往返与 evaluate 本身只有毫秒级。
2. `worker.py` 在模块导入阶段就 `from . import properties`，连**不查物性的控制 Worker**
   也要为 CoolProp 付 1.5 s；同时 `worker.py` 顶层还导入了 `.runtime`（连带 models/pydantic）。
3. 因此 W1 的切入点明确：把 `properties` 与 `runtime` 从 Worker 入口的 **eager import** 链里拿掉，
   控制 Worker 不需要 CoolProp；普通模块 Worker 只在真正访问 `ctx.fluid` 时再导入。
4. 需物性任务的总成本不会因此消失（只是从初始化后移到首次物性访问），所以 W1 必须同时测
   “首个成功步”是否回退，不能只看初始化时间。
