# FluidNet 与倍思鹿的当前差异

核对日期：2026-10-15。FluidNet 基线：`fluidnet-prototype-engine` v0.4.6，最新提交 `2301796`。本次计入 Python 项目控制、SQLite 保存与运行归档、备份恢复、独立项目修订、模块升级预览与回退、工况编辑和结果对照。

倍思鹿侧使用当天获取的 12 篇官网教程、V1.1 多线程说明的既有核对记录，以及公开界面截图。安装教程列出 6.29 下载，其他材料涉及多个版本，因此只比较资料明确描述的能力。未运行倍思鹿程序，未取得 NET 内核源码；已有一项外部泵部件快照复算，尚无双方完整同工况的精度或性能对测。

## 判断

FluidNet 已具备单相管网建模与求解、Python 设备模块和项目控制、PID、后台会话、变量接口，以及可靠保存和建模版本管理的主要链路。项目控制和服务重启后读取历史已不是待实现项；当前画布也已具备同屏曲线观察。

倍思鹿公开资料呈现的覆盖面更广，剩余差距主要在工业设备模型、闭式容器和可压缩流动等物理模型、设计函数与源码断点调试、真实设备/第三方程序接入，以及 Windows 发布部署。FluidNet 已实现的单位合同、模块快照与双哈希、状态提交和修订冲突保护可由测试验证；公开资料不足以判定倍思鹿是否具有相同细节。

## 计算架构的具体差别

**倍思鹿参考架构**：主控 EXE 解析拓扑；不同模块 EXE 并行计算，主控检测模块完成后调用 NET DLL，再进入下一轮。数据 DLL 提供模块变量和控制指令的统一读写入口。说明允许轻量模块合并、重型模块单独执行。[P，第 1、3–4 页]

**FluidNet 当前架构**：FastAPI 接入，RunManager 调度动态会话，SimulationSession 管理设备状态/PID/采样控制，SciPy 求解全网水力与热力。自定义 Python 模块和项目控制通过行式 JSON RPC 在独立 Worker 执行，成功子步再提交受管理状态。内置设备在主服务中计算；SQLite 事务保存项目修订和有界运行历史。

| 具体项 | 当前差别 |
| --- | --- |
| 全网数值方法 | 我方可确认是 SciPy least_squares，默认 dense、可选 sparse Jacobian；参考资料没有足够信息还原 NET 的内部算法 |
| 支路定义 | 参考说明将多个串联设备通路组成一条计算支路；我方每条启用的设备通路形成一个 CompiledBranch，尚未做串联压缩与连通分块调度 |
| 并行粒度 | 参考架构按模块程序分工；我方有 2 个后台计算线程，Python 模块可按 1–16 个 Worker 分片批量求值，默认 1 片。每实例状态独立 |
| 数据交换 | 参考走原生 DLL/PIPE 等接口；我方内部 Worker 采用 JSON 管道，对外使用 HTTP/WS；调用频率、数据体积和一致性语义都不同 |
| 状态提交 | 我方显式区分重复 evaluate 与成功子步 commit_step；公开材料不足以确认参考系统在失败重试中的完整状态提交规则 |
| 模块追溯 | 我方项目绑定完整模块快照与双哈希，后续发布不影响旧项目；参考教程没有足够版本策略细节支持同级比较 |

相关源码：[compiler.py](../backend/fn_engine/compiler.py)、[solver.py](../backend/fn_engine/solver.py)、[thermal.py](../backend/fn_engine/thermal.py)、[simulation.py](../backend/fn_engine/simulation.py)、[jobs.py](../backend/fn_engine/jobs.py)、[runtime.py](../backend/fn_engine/runtime.py)、[batch.py](../backend/fn_engine/batch.py)、[packages.py](../backend/fn_engine/packages.py)。

## 三处需要避免混淆的比较

### 两相物性与两相流网络

倍思鹿入门文章明确写着“目前还没做到两相流计算的底层支持”。冷库案例可以在设备模块里描述气液状态、罐体和制冷循环；这些内容不能单独证明具备通用两相管网求解器。该案例也列有模型简化，AI 训练与效果检验仍在进行中。[B00][BC]

FluidNet 可查询两相物性，但网络流动只支持与所在回路边界一致的单相。当前计划明确排除管网两相流、水锤和完整可压缩流动；若目标转为覆盖复杂制冷或燃气案例，需要另设物理模型项目。

### 容量、读写速度与求解速度

| 资料或实现中的数字 | 正确含义 |
| --- | --- |
| 倍思鹿 V1.1 的 10 个项目、1110 支路槽位、每支路 55 个单元、单项目 40000 模块槽位 | 该说明中的接口数组配置，不能当作同规模实时性能验收 [P，第 5–7 页] |
| 倍思鹿的小项目约 200 次迭代/秒、大项目 30 次以上/秒 | 作者报告，缺少本次可复现的统一算例、精度和硬件条件 [P，第 1 页] |
| 倍思鹿数据 DLL 的 800 万次读写/秒、曲线文章的高频刷新数字 | 变量访问或曲线通道指标，与一次全网物理求解不是同一测量对象 [P，第 7–8 页][B07] |
| FluidNet 后端最多 1000 实例、最多 20 个活动后台运行 | 当前模型及运行管理配置；不表示 20 个复杂项目能同时满足实时节奏 |
| FluidNet 画布每页最多 64 个设备、每项目最多 8 页 | 当前前端限制，需要与后端容量分别说明 |
| FluidNet 已有 9 组规模记录：1000 实例串联 2.736 秒、分支 1.955 秒、25% Python 模块网络 7.205 秒 | 本机 sparse 算例各测一次，耗时不含编译与序列化；是后端规模观测，未形成与倍思鹿的统一对测 [备份与工程验收记录](BACKUP_ACCEPTANCE.md) |

如需比较速度和精度，应先统一拓扑、设备曲线、工质、初值、边界、状态模型、容差、输出频率与硬件，分别测量求解时间、RPC、历史记录和界面开销。

### 界面重连、历史保存与跨重启续算

倍思鹿部署教程描述了关闭界面不影响后台、重新打开界面恢复显示；型号教程明确描述磁盘 JSON 保存。V1.1 PDF 第 8 页同时写明其调用说明尚未涉及工况保存设计。现有材料不足以确认所有变量历史的磁盘保留策略或任意时刻的跨进程重启续算。[B05][B09][P]

FluidNet 已有页面关闭后后台继续运行、SQLite 项目与运行归档、模块版本文件及 ZIP 备份。服务重启后可读取已保存项目、最近窗口和全程抽稀，未结束运行标为 interrupted。当前归档保留最近 20 条终态运行，完整工作区和独立项目各保留最近 5 修订。重新计算需要新建运行，跨重启继续原仿真仍待检查点设计；24 小时持续运行终态验收尚未完成。不能仅根据双方都使用“数据库”“恢复”字样推断行为等价。

## 目前值得保留的基础与下一步

我方已经形成的基础包括：Pydantic 严格合同与自动生成接口说明、显式单位、草稿/应用语义、模块版本快照与双哈希、受限参数写入和可关联命令回执，以及成功子步提交状态的约定。这些是本项目可验证的工程特性；不据此推断参考软件没有相应机制。

最新代码在提交前通过 313 项 Python 测试、10 组浏览器验收和 5 项样例验证；本次比较复用这些结果，没有再次执行。样例包含一项外部缓存泵部件、四项仓库回归或解析验证。倍思鹿 TEST 的 MOD2 泵质量流量参考 8.0486127506 kg/s，复算 8.0486120081 kg/s，绝对误差约 7.43e-7 kg/s。这是固定入口/出口压力下的泵部件水力复算，不能扩展为整套制冷系统精度或性能结论。验证入口和边界见 [建模工作流验收说明](MODELING_TRIAL_VALIDATION.md)。

下一步按使用目标推进：

1. **稳定交付当前范围**：完成离线 Windows 便携包、干净机器安装/升级、24 小时运行终态和实际项目保存恢复验收。
2. **工程建模效率**：补设计函数真实执行、源码调试、型号批处理和大项目操作；把已实现的版本、工况流程放入实际建模任务验证。
3. **可编程控制与设备接入**：在现有 Python 控制和变量接口上补别名映射，选一个明确的串口/PLC 协议接真实设备。
4. **复杂制冷或燃气应用**：围绕实际项目补压缩机、止回阀、闭式容器、可压缩管道和必要组分/相态模型，分别确认公式与验收数据。通用两相管网仍属于额外物理专项。
