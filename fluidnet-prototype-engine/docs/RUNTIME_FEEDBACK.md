# 运行推进与实时读数

更新日期：2026-11-11。本轮根据“运行中参数更新慢”的反馈，分别检查计算推进、参数接受与界面更新。没有与倍思鹿在同一设备、同一模型和同一计数口径下对测。

## 使用方式

画布右侧“运行设置”中的求解页现在提供已有的“计算节奏”和“速度倍率”：

- **按真实时间运行**：1 倍时，1 秒仿真时间按约 1 秒墙钟时间安排；求解本身更慢时仍会落后。
- **速度倍率**：加快实时模式的计划推进速度，实际仍取决于计算能力。
- **快速计算**：不主动等待真实时间，尽快推进到仿真终点；持续运行则保持计算，直到停止。

活动运行中这些设置锁定，停止后再调整。没有改变已有项目的默认模式、物理时间步长或收敛容差。调小时间步会改变计算工作量与时间离散，不等同于加快界面刷新。

## 实时读数通道

当前活动项目通过现有 WebSocket 接口接收完整结果帧，默认请求间隔 50 ms。只有新的有效完整帧才进入实时读数；同一绘制周期只保留最新一帧。它不修改设备参数草稿、历史帧、曲线偏移或归档确认。

历史、事件、命令回执及终态继续使用 HTTP，保持原有约 200 ms 的轮询。曲线重绘与即时设备数字分开，避免每次数字更新都重画整段曲线。没有新数据时跳过重复绘制。

切换项目、替换运行或关闭页面会清理原连接；浏览器往返恢复页面后重建连接。WebSocket 不可用、服务器仍使用旧协议或有限重试失败时，继续使用 HTTP 轮询。客户端必须同时校验项目对象、运行对象、运行 ID、帧序号及参数修订，迟到结果不能覆盖新结果。

## 同条件浏览器对照

对照使用同一个临时后端、同一个 Edge 进程和独立浏览器上下文。9 设备泵阀并联管网关闭控制脚本，动态持续运行，时间步 0.02 s、实时 1 倍；观察窗口约 4 秒。优化前四个前端文件由快照固定，优化后读取当前源码。

| 指标 | 优化前 | 优化后首轮同条件对照 |
| --- | ---: | ---: |
| 后台接受帧 | 约 50 帧/s | 约 50 帧/s |
| 设备显示的不同采样时刻 | 5 次/s | 约 19.75 次/s |
| 显示更新间隔中位数 | 200 ms | 55 ms |
| 一次开度 80%→40%，请求至显示真实流量下降 | 370 ms | 112 ms |

上表排除了仅“最近完整帧”等文案后缀变化。帧/s 是已接受的结果帧数量，不是牛顿迭代、残差计算或 Worker 调用次数。参数响应只有一次操作样本，不代表延迟分布；最终源码的补充采样独立登记，不替换原同进程对照。

高频读数增加本地传输：这次 4 秒窗口的 HTTP 仍约 40 次、1.86 MB，另收到约 0.73 MB 的 WebSocket 消息。只有当前项目使用快通道。没有据此声称所有大型制冷工程都能达到相同显示或计算速度。

最终源码独立复验为约 17.98 次/s，更新间隔中位数 60 ms；一次参数请求至可见流量变化为 127 ms。实际加载的五个前端文件哈希与最终磁盘内容一致，无显示时间回退或页面错误。

原始证据位于 `artifacts/runtime-feedback/browser-before.json`、`browser-after.json`、`browser-comparison.json`。`scripts/profile_runtime_feedback.mjs` 顶部给出复跑方式；需要保留优化前的前端文件快照，不能把当前代码两次运行当作前后对照。
